# 核心字段片段原型 v1（2026-10-19）

用户确认的范围是标题、时间、地点转备注，允许部分表达需要确认。“50%”按核心能力范围理解，没有将其设为准确率门槛。本轮是中文离线逻辑原型，未替换现有 v3 或修改客户端。

## 实际必测例

当前 ONNX 权重及生产 KMP 日期解析实跑：

```text
输入：明天下午 4 点要在逸夫楼开会
参考时间：2026-10-19 12:00，Asia/Shanghai

标题：开会
截止时间：2026-10-20T16:00
备注：地点：逸夫楼
状态：COMPLETE
```

模型抽取原文片段：TIME=明天下午 4 点、CONNECTOR=要在、LOCATION=逸夫楼、TITLE=开会。地点名不经过字典查找；日期由生产 KMP 计算。连续空格变体同样成功。“讨论逸夫楼改造方案”保留完整标题，不抽取地点。

## 实现与比较

复用现有 UER tiny WWM 编码器和 v3 编码器权重，仅替换任务头：一次编码整句，对所有有效 token 起止对打分，角色为 TITLE/TIME/LOCATION/NOTE/CONNECTOR；另有支持单事件请求/需要确认的判定。候选冲突、未解释原文和低置信请求生成待确认草案，保留原文及已识别字段。

时间字段是模型预测的原文，交给现有 Native 适配器中的生产 QuickAddParser，要求时间被完整消费、占位标题不变，才采用日期。Python 中的语义组装是参考实现；本轮没有实现新的生产 KMP span codec。PARTIAL/CONFIRM 的 ready=false，不能把部分识别计为完整正确。

语料：5000 条训练、360 条开发、480 条合成留出、16 条已曝光回归。train/dev/test 的标题与地点字符串隔离；新增 dev/test 标题与地点也未在 v3 业务训练中出现。包含内部否定词、标题中的时间/地点名、空白连续段、备注、分离的日期与钟点，以及否定、条件、多事件、缺事件等确认请求。上游语言预训练是否见过这些词语不作未见声明。

两种新模型均从同一编码器权重初始化，训练相同数据 8 epoch，seed42、batch24，encoder lr3e-5、任务头 lr5e-4；按 dev 指标选检查点。BIO 对照也加入 LOCATION/CONNECTOR 标注，并正确保留 token 间连续空白，帮助区分新数据/标签与结构的收益。损失与头结构不同，只是单 seed、同预算原型对照。

最终阈值仅从 dev 网格选择：片段 score>=1、请求支持概率>=.9；BIO token log-odds>=0、请求支持概率>=.98。test/回归没有参与选择。

| 首轮合成留出：480条，384条应接受 | 完整正确 | 已接受中的错误 |
| --- | ---: | ---: |
| 直接片段 | 244/384（63.54%） | 0/244 |
| 相同数据 BIO | 222/384（57.81%） | 5/227 |
| 原 v3 | 31/384（8.07%） | 34/65 |

v3 对照没有地点/连接词的新标注，因此与 v3 的大幅差异同时包含数据、能力范围与结构变化，不能全部归因于片段头。相同数据 BIO 与片段差异为 5.73 个百分点，仍需更多训练重复验证。

片段模型留出正例中，包含待确认草案的字段保留精确率：title=81.51%、dueAt=93.49%、note=85.42%；这些不是可自动采用的完整成功率。留出 TITLE/LOCATION/TIME 边界 F1 分别为 87.11%/85.28%/94.90%。

未见语序只做对 12/58 个正例，是主要短板。已曝光回归 9/12 完整正确，三个失败例分别为：

- “明天下午4点在逸夫楼开会”：字段均正确，请求判定置信度不足，待确认。
- “明天下午4点开会，地点逸夫楼”：地点引导没有冒号，残余内容需确认。
- “明天下午4点开会，备注：地点逸夫楼”：地点未充分抽取，待确认。

## 日期层的独立问题

对 dev/test/回归的 684 个正例注入正确标注，仅作契约诊断，670 条完整正确、14 条被日期规则拒绝，全部涉及“上午十点”。生产 QuickAddParser.number 在单字分支返回了不包含“十”的数字表结果，提前返回 null，后续十进位分支无法执行。时间片段正确也会遇到此现有缺陷。

本轮保留生产解析器不变，记录该缺陷并让原型返回待确认；没有将这 14 条当成模型抽取错误，也没有修改金标迎合规则。此前用于检查“所有正确标注是否都通过”的诊断断言发现这 14 个失败；它不是全部通过的检查。Python 行为测试不包含这个未修改的 KMP 实现，37 项测试通过。

## 产物与验证

- 模型 3,226,316 参数，ONNX 12,877,422 字节；检查点选择第5 epoch。
- dev/test/回归共856条，PyTorch 与 ONNX 数值最大差约1.17e-4，实际字段、状态与完整提案差异为0。
- 数据、权重、适配器及源码 SHA 保存在 `artifacts/zh-core-spans-v1`、`reports/zh-core-spans-v1`；版本控制证据见 [evidence/core-span-prototype-v1.json](evidence/core-span-prototype-v1.json)。
- 本轮没有 Core ML/MindSpore 导出、三端 codec 集成、手机延迟或真人金标；这些构造样例不能证明真实用户准确率。

## 运行

```sh
PYTHONPATH=src HF_HUB_OFFLINE=1 TOKENIZERS_PARALLELISM=false \
  ../DeadlinerCore/build/quickadd-env/bin/python -m quickadd_training.span_predict \
  '明天下午 4 点要在逸夫楼开会' --now 2026-10-19T04:00:00Z
```

主要入口：`span_data` 生成/校验数据，`span_train --allow-synthetic` 训练并导出，`bio_control --allow-synthetic` 训练同数据对照，`span_evaluate` 校准及评估，`span_evaluate --verify-existing` 对照完整 ONNX 提案。生成、训练、评估默认拒绝覆盖已有目录；重跑需使用新输出路径。生产 v3 未被替换。

用户后续要求的独立标准化实验，见 [normalization-comparison-v1.md](normalization-comparison-v1.md)。
