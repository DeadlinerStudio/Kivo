# MVP 模型完整 Review（2026-10-19）

本次审查对象是三端源码资源中配置的 `quick-add-zh-v3.0.0` / `quick-add-en-v3.0.0`。中文底座为 UER tiny WWM，英文为 BERT tiny；早期字符 CNN 的结果只用于历史对照。审查覆盖业务微调数据、训练入口、意图/槽位、WordPiece 字符映射、生产 KMP 日期归一化、拒绝策略、评测与发布门禁，并静态检查三端语言选择与结果接入。

**主要结论：当前 MVP 学到了较窄模板下的识别能力，同时存在意图分类的词汇捷径、确定的字符映射缺陷，以及训练和解析能力的缺口。单独增加训练轮次或降低阈值，收益有限。**

此次未更改生产代码、权重、清单、阈值或线上配置。新增两个离线审查脚本与本报告。完整机器结果在 `reports/mvp-review-2026-10-19`（Git 忽略），可保存的紧凑证据在 [evidence/mvp-review-2026-10-19.json](evidence/mvp-review-2026-10-19.json)。

## 2. 优先问题

### P1：意图分类把标题中的否定词误当成“不添加”

冻结集中文 212 条漏识别中，92 条由高置信度 OTHER 直接拒绝，集中在三个标题家族：

| 标题 | OTHER 拒绝 / 该标题正例数 |
| --- | ---: |
| 检查打折商品有没有库存 | 36 / 36 |
| 去商店退掉不合适的衣服 | 36 / 36 |
| 确认租的车还有多少油 | 20 / 36 |

这三个标题家族的 108 条正例最终全部未覆盖。中文共有 5 / 40 个留出标题家族的 36 种组合全部失败；这些家族贡献了 180 / 212 条漏识别，说明错误高度聚集。

实际权重的配对诊断更直接：

| 输入 | TASK 概率 | OTHER 概率 |
| --- | ---: | ---: |
| 明天下午3点检查商品库存 | 99.9999% | <0.0001% |
| 明天下午3点检查商品有没有库存 | <0.0001% | 99.9997% |
| 明天下午3点退掉衣服 | 99.9999% | <0.0001% |
| 明天下午3点退掉不合适的衣服 | <0.0001% | 99.9997% |
| 明天下午3点记录原因 | 99.9999% | <0.0001% |
| 明天下午3点记录取消原因 | 0.0026% | 99.9974% |

这些都是明确添加请求，否定或取消描述的是任务内容。如此高的错误 softmax 分数也说明“提高置信度门槛”无法修复这些输入。

数据证据：中文 29,703 条业务训练中，正例 TITLE 含“不”=0、含“没”=0、含“取消”=0；对应负例全文分别有 894、320、555 条。这个偏差与配对诊断一致，强烈支持模型学习了表面词汇捷径的判断；尚未通过重训消融证明各因素的独立因果贡献。

相关位置：[corpus.py](../src/quickadd_training/corpus.py) 的正例 TITLE_POOL 和负例模板；[pretrained_teacher.py](../src/quickadd_training/pretrained_teacher.py) 的三分类意图头；Core `QuickAddCharacterCodec.kt:46–52`。

处理方向：补充内容含否定词的正例与真正取消请求的配对标注，例如“退掉不合适的衣服”/“不要提醒我退衣服”、“记录取消原因”/“取消记录原因的任务”。按语义家族留出评估，分别统计 TASK→OTHER 与真实负例误接受。

### P1：连续空白在 WordPiece 到字符映射时被断开

实际模型中，`明天下午 3 点打电话` 接受，`明天下午  3  点打电话` 拒绝。英文相应变体也复现。

为排除模型预测差异，另给两句注入完全正确的 **token** BIO logits：

- 两句 input IDs 相同，attention mask 相同，注入的 token logits 相同。
- 单空格版本得到“打电话，2026-10-20T15:00”。
- 双空格版本返回 null。

原因是映射只检查空白字符紧邻的左右字符。连续空白的第一个字符右侧仍是 O，不能桥接；随后出现 I-TIME 时因 BIO 不连续而拒绝。

位置：Core `QuickAddWordPiece.kt:84–90`；Python 同类问题在 [pretrained_teacher.py:30](../src/quickadd_training/pretrained_teacher.py) 的 `character_logits`。单元测试仅覆盖单个空格，未覆盖空白连续段。

处理方向：以连续空白段为单位、结合两端实体标签恢复映射，保留原文 Unicode 偏移。覆盖普通/全角空格、tab、连续多个空白，以及不同实体之间的空白；不同实体仍须保持边界。

### P2：WordPiece 模型仍先经过旧字符词表的未知比例门槛

`明天下午3点给Zoë打电话` 的 WordPiece 未知 token 数为 0，但原文 `Z`、`ë` 不在辅助字符词表中，比例 2/13=15.38%，超过 10%，在执行模型前就被拒绝。

位置：Core `QuickAddCharacterCodec.kt:15–24`，先 `tokens(text)` 再 `wordPiece.encode(text)`；[benchmark.py:62](../src/quickadd_training/benchmark.py) 也复现同一门槛。

这个约束使用原始字符词表；模型实际使用的 WordPiece 支持小写、去重音和子词分解，两种未知标准不等价。英文系统下输入中文会命中更大的语言覆盖问题，不能仅靠修改该门槛解决。

处理方向：分别定义字符模型和 WordPiece 模型的编码有效性，用实际 token 覆盖和 tokenizer 归一化判断后者；保留长度、非法字符及上下文溢出检查。这个例子证明当前门槛会额外拦截可编码输入，尚未证明移除门槛后该例完整识别必定正确。

## 3. 数据与训练目标的缺口

| 最终业务训练统计 | 中文 | 英文 |
| --- | ---: | ---: |
| 训练行数 | 29,703 | 27,935 |
| annotationStatus=synthetic | 100% | 100% |
| 不同 TITLE 字符串 | 465 | 376 |
| 不同 TIME 字符串 | 88 | 231 |
| 不同 REPEAT 字符串 | 14 | 28 |
| NOTE 标注数 | 0 | 0 |
| preferredKind=TASK | 100% | 100% |

业务微调有约三万行，但大量是标题×少量时间模板×布局/空格组合。预训练底座包含上游语言知识；这里的“全合成”特指此次业务微调数据，不表示底座从未见过自然语言。

**备注头没有正向监督。** 模型有 B/I-NOTE 输出，但训练集中 NOTE=0。中文三个带显式“备注：”的样例全部失败，输出将备注混入 TITLE/TIME 或产生非法 BIO；注入正确槽位后这三例均能通过。首要缺口在业务标注与学习目标。

**日期语法覆盖不充分。** 新诊断中两种语言各 6 条日期扩展只识别 1 条。中文“10月25日下午3点”“2026年11月1日下午3点”“2026-11-01 15:00”实际模型均失败，提供正确槽位则能归一化，说明这些例子有明显抽取缺口。中文三天后/半小时后、英文月份名称/相对时长，即使提供正确槽位仍失败，属于归一化支持边界。它们需要产品范围与解析实现共同确定。

**日常请求措辞被白名单约束。** 中文“麻烦提醒我”“记得要”，英文“I need to”“don't forget to”等，即使正确抽出标题与时间，未分配词语也可能因 `neutralGap` 白名单而拒绝。双语措辞诊断各 5 条只通过 2 条。应定义允许的请求修饰语和真实限定语，避免把无害语气词与“之后/如果”等改变语义的词混用同一处理策略。

**显式选择 HABIT 的含义没有贯穿模型。** 新诊断中选择 HABIT 后只输入“喝水”/“drink water”均失败。训练输入不包含 preferredKind，所有训练行的 preferredKind 也都是 TASK。运行时先拒绝 preferredKind=HABIT 且预测 TASK；即使 oracle 强制预测 HABIT，没有 REPEAT 仍拒绝。若产品允许在习惯入口只填名称并使用默认每日配置，这就是确定的接入契约缺口；若要求输入周期，应在范围和交互中明确。

相关位置：Core `QuickAddCharacterCodec.kt:74–96` 的 gap、kind 与 repeat 约束；`QuickAddTemporalNormalizer.kt` 和 `EnglishQuickAddFields.kt`；[pretrained_teacher.py:49](../src/quickadd_training/pretrained_teacher.py) 的模型输入与独立 token 分类头。

当前模型使用逐 token 交叉熵，无序列 BIO 约束；这与运行时严格拒绝非法 BIO 的组合，使边界小错直接变为全句拒绝。后续可比较合法 BIO 约束解码或 span 预测，但它们不能修复 OTHER 错分，也不应先于数据补齐和确定的映射缺陷。

| 阶段 | 中文 | 英文 |
| --- | ---: | ---: |
| 高置信度 OTHER | 92 | 0 |
| 意图概率或 margin 不足 | 13 | 0 |
| 槽位置信度不足 | 99 | 58 |

固定 intent=.85、margin=.25、slot=.9 直接沿用了 v2；未看到针对 v3 的独立校准证据。slot 门槛作用于全部有效字符，也包括 TITLE 和 O，一个字符不足即全句拒绝。

仅作离线消融，保持权重、意图阈值及其余逻辑不变：

| slot 阈值 | 中文冻结集正确数 | 英文冻结集正确数 | 中文新诊断正确数 | 英文新诊断正确数 |
| --- | ---: | ---: | ---: | ---: |
| 0.9（现有） | 1228 | 736 | 32 | 31 |
| 0.8 | 1243 | 745 | 33 | 32 |
| 0.7 | 1246 | 747 | 33 | 33 |
| 0.5 | 1255 | 759 | 33 | 33 |

本次样例中这些重放均未产生错误接受，但负例规模与覆盖不足，不能据此修改生产阈值。中文 slot=.5 只增加 27/1440=1.875 个百分点，诊断集仅多 1 条，主要缺口仍在。

共享 `QuickAddLocalRecognizer` 已区分 unavailable 与 semantic rejected，REJECTED 不再回退规则；本次没有发现旧版本“模型拒绝后规则重新误接受”的行为重新出现。诊断原因为 null 或通用 REJECTED，线上很难从表现区分编码、意图、槽位、gap、日期等阶段；建议给内部诊断增加稳定 reason code，以便回归与排障。

## 5. 评测覆盖与质量门禁

**现有冻结集主要衡量“熟悉时间模板下的新标题”。** 中文 1440 个正例=40 个标题×18 种时间×2 种布局；英文 800 个正例=40×10×2。两个冻结集 HABIT=0、NOTE=0，日期仍集中在明天/后天/大后天的有限组合。40 个标题有真实留出价值，但大量组合高度相关，不能当成 1440/800 种独立自然表达。

本次验证最终 train/dev/test 无规范化全文或 group 跨 split 重叠，最终训练与测试的 TITLE 字符串也无重叠。**没有发现这些集合的直接文本泄漏证据。** 问题是语法、语义和产品功能的测试覆盖不足。旧 dev 也主要复用标题词汇池；中文旧 dev oracle 教师报告覆盖 97.92%，与新标题冻结集 85.28% 的落差说明应持续单列泛化评估。这份教师报告来自归档，不能与端侧导出的当前新推理混称为同一测试运行。

**发布门禁缺少绝对可用性下限。** [gate.py:25](../src/quickadd_training/gate.py) 只要求覆盖率相对规则提升 5 个百分点，没有最低正确覆盖率及功能分组下限。构造规则覆盖 0%、候选覆盖 6%、错误接受 0%，其余证据字段设为通过的逻辑 fixture，`reasons()` 返回空列表。这个 fixture 仅测试门禁逻辑，未提供任何真实发布证据、未触发发布。建议加入每种语言、TASK/HABIT、日期/备注/否定对照等分组的绝对下限，并给小样本错误率附带不确定性说明。

**预训练入口缺少原 CNN 入口的若干数据保护。** [train.py:25](../src/quickadd_training/train.py) 有 train/dev 校验、locale 检查、人工标注或显式 synthetic opt-in、数据哈希前后检查；`pretrained_teacher.py` 直接读取 train，未调用同样的校验，也没有 synthetic opt-in，默认评估 dev/test/regression，保存最终 epoch 权重而不基于 dev 选择检查点。这不证明此次数据泄漏，当前数据另行校验通过，但使未来迭代容易失去防护；应统一两个入口的数据和评估流程。

## 6. 端侧接入与未覆盖范围

- 三端源码资源中的双语 manifest 均与本机 v3 一致；不等价于确认用户当前手机实际运行的 APK/IPA/HAP 或缓存状态。
- Android、iOS、Harmony 均按系统语言选择 en 或默认 zh，没有按当前输入语言路由。英文系统输入中文、中文系统输入大量英文/姓名，需作为独立场景验证；当前诊断中的英文模型中文标题在字符门槛阶段被拒绝。
- 三端源码均有约 100ms 输入等待与异步结果防过期逻辑。冻结 benchmark 不包含这部分 UI 与真实设备时延；本次未测真机输入、下载失败恢复、冷启动及 UI 提交链路。
- 归档三格式 parity 证据为通过，本次 ONNX 重推理/生产 KMP 复放也稳定。因此在已测样例内，数据、学习和共享解码层有充分的直接问题证据。本次没有重新执行 Core ML、MindSpore 或三个手机端，仍不能排除设备特有问题。

## 7. 建议执行顺序

1. **先修可确定复现的共享解码问题**：连续空白、WordPiece 前的字符门槛；明确 HABIT 入口与无周期标题的默认契约；加入分阶段拒绝原因。用现有权重先比较修复前后，隔离实现收益。
2. **补全对照数据和业务范围**：首先添加标题内部否定词与真正否定请求的配对数据、绝对日期、显式备注、自然请求措辞。相对时长、英文月份名称等先确定是否纳入 MVP，再补对应归一化与标注。保留已暴露的 g4/g5/g6 和本诊断集作开发回归。
3. **重建独立评估再做模型实验**：按来源、语义、时间语法、标题家族隔离，覆盖两种语言、TASK/HABIT、备注、姓名/符号、明确负例与确认请求。先独立人工复核一批真实用法，冻结最终测试；dev 用于 checkpoint 选择、阈值校准及结构比较。此次审查后继续利用的 g6 不再承担未来盲测角色。
4. **再比较训练与结构**：保持同一数据和生产解码器，比较修正数据后的现有 tiny BERT、合法 BIO 解码、span 头及更强底座；分开记录数据、结构、阈值收益。持续看完整提案覆盖率与错误接受，也单列各阶段和语义家族失败率。
5. **最后完成产品验收**：补绝对覆盖率与功能分组门禁，验证三端真实 UI、模型版本、缓存、冷启动和延迟。打包、下载及导出一致性分别验收。
